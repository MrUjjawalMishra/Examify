# Integrated staging architecture

The existing production Worker `examify` is excluded from this rollout. Staging uses `examify-staging` as a single-origin React asset host and control-plane gateway, a separate control D1 database, and two dedicated school slots. Each slot has its own Worker, D1 database and private R2 bucket. School Workers have no workers.dev, preview or custom routes.

Owner-created schools reserve a unique slot transactionally in the control registry. A cryptographically random immutable school ID is written into that slot's singleton tenant identity. A service-binding-only initialization request creates the initial administrator with a salted password hash. The registry becomes active only after successful initialization. Repeating the same request ID reuses the reservation and safely finishes initialization; an occupied slot never changes school identity. No database identifier or service-binding name is accepted from a client.

The gateway resolves `/s/CODE/api/*` through the active registry and a fixed deployment-controlled binding allowlist. It replaces the internal authorization header. Tenant Workers verify the internal secret and their own D1 identity and status on every authenticated request. School and owner session cookies have separate names; school session tokens cannot resolve in another school's database. Switching school signs into a different school session on the same browser. There is no public owner bootstrap endpoint.

Suspension denies routing centrally before updating the tenant. Reactivation updates the tenant first. Failed operations remain retryable. Audit records accompany provisioning and account changes. Resource deletion, reassignment and production migration are deliberately absent from the application API.

This staging implementation preprovisions two isolated slots, rather than giving the public Worker Cloudflare account-management credentials. Capacity exhaustion is explicit. An operator expands the pool with another migrated Worker/database/bucket and a reviewed gateway binding. The initial five-school production target requires five slots; automatic unbounded infrastructure orchestration is not implemented. This preserves the dedicated-school architecture while limiting staging resource creation.

Apply versioned migrations with Wrangler's migration ledger before deploying tenants. Keep INTERNAL_KEY in Worker secrets, never checked-in configuration. Bootstrap the owner using the operator-only script and a local ignored credential file. Staging must contain only fabricated users. Private image objects are accessible only by their authenticated uploader in the initial media API; sharing with examination evaluators will require a separate assessment authorization policy.
